## Reading the table
- Banks $86-$93, $96-$99, $9C-$9D, $A0-$A4, $A7-$A9 and $AD-$B2 are byte-identical in most regions: objects, sprite graphics,
  most tile graphics, palettes and the audio banks are shared (JP differs slightly in $94, $95, $9E, $A9).
- Code banks $80-$84 differ in every region; EU and DE share most of their changes against US (bank $81 and $84 differ by about
  the same amount), JP differs mainly in $80, $82 and $83.
- Graphics that differ per language are concentrated in $9A, $9B, $9F, $A5 and $A6 (text/title/menu graphics).
- AI script banks $B3-$B5: EU/DE differ from US in $B3-$B4; JP in $B5.
- Dialog banks differ everywhere (different text), JP additionally has its text in $AA-$AC.
Next step for the unified tree: DE code banks $80-$85 are done (see below); EU and JP code are next, then the
differing graphics, dialog and AI banks.

## DE code banks $80-$85 (patch blocks on the US source)

The German code is not a second copy of the sources. It is expressed as `if !REGION_DE ... else ... endif` blocks
inside the US modules (`src/code/bank_80..85`), so every function keeps its US name and everything that is identical
is shared. `python3 tools/build.py --region DE` defines `REGION_DE=1`, assembles banks $80-$85 and compares them with
the reference hashes in `tests/expected.json` (key `DE`, limited to banks $80-$85; the ROM itself is never stored in the
repository). The US build (`!REGION_DE = 0`) is unchanged and bit-identical.

How the DE code relates to the US code:
- **Relocation only (about 10 % of the bytes).** Most differences against US are not logic changes: the code after the
  first DE insertion moved, and WRAM from `$7E08D1` on is **6 bytes higher** (`strcNames.wWeekday` is 6 bytes longer in
  DE: longer weekday names). Labels and RAM names follow automatically: `!DE_RAM_SHIFT` (6 for DE, 0 for US) is added to
  the RAM equates and structure bases in `src/common/ram.asm` and `structures.asm`. Hex literals that point into the
  shifted block (`STA.W $09A3`, `STA.L $8019B6`, `dl $800917`) got `+!DE_RAM_SHIFT` in the US text (no block needed).
  The shifted range is `$08D1-$1FFF` (abs/dp/WRAM mirror); `$7E2000` and up (OAM/DMA queues) did not move.
- **Same bytes (about 86 %).** Identical in DE, shared with US.
- **DE specific (about 4 %).** Wrapped in `if !REGION_DE` blocks: the weekday/ordinal text routines
  (`game_events.asm`), the dialog variable/number drawing (`dialog.asm`, including the `aTextDataTableFFFD` table), menu
  and main-loop text positions (`main_loop.asm`, `menu.asm`, `system.asm`), pointers to the DE graphics blobs in banks
  $9A/$9B/$A5 (`tilemaps.asm`; those banks are not part of the unified tree yet, so the DE block holds the raw address)
  and a few constants. Inside a block the DE text uses the US label and RAM names where the alignment finds the
  counterpart; branch targets without a US label get `.de_<addr>` labels (or the `L_<addr>` equates in
  `src/code/de_targets.asm`). The ROM header (maker code, game code, country, checksum) is patched in `header.asm`.

Method (tools, all in `tools/analysis/` and `tools/migration/`):
1. `bytealign.py` aligns the DE bank with the US bank (anchor diff + edit-distance refinement) and gives a byte-exact
   US->DE address map.
2. `usmap.py` gives every line of the US sources its ROM range (from the `;ADDR|BYTES|` comments) and its M/X state.
3. `align_regions.py` classifies each line (same / relocated / DE specific). Label addresses in DE come from the
   operands of the aligned instructions ("this `JSL fFoo` is `JSL $82CCC6` in DE, so `fFoo` is at $82CCC6"), which is
   more reliable than the byte alignment inside short coincidental matches.
4. `disasm65816.py` (65816 disassembler with M/X tracking, round-trip tested on all US code) turns the DE bytes of every
   DE specific block into asar source (`de_variant.py` chooses US names), `migration/de_patch.py` writes the blocks.
   It is a one-shot migration tool (it expects the unpatched US sources and the DE ROM); the result is verified by
   the DE build.
